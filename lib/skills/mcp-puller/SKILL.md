# MCP-Puller

用户用自然语言要求「安装 / 接入 / 添加一个 MCP 服务」（贴出仓库链接、README、安装命令或参数）时，按本流程执行。用户没有要求安装时不要安装，也不要主动改动 MCP 配置。

## 1. 理解用户给了什么

- 从用户消息里提取：名称、传输方式（本地 command + args，或远程 http(s) URL + headers）。
- 用户给出的命令与参数原样保留，不「顺手优化」、不补自己猜的 flag。
- 缺失关键信息（本地没有命令、远程没有地址）时先问清楚，不要猜。
- 不需要工作区：MCP 安装只写 Yan 自身的 MCP 配置（Yan 运行时目录），不属于用户交付物，Blank（未选择工作区）下同样直接执行，不要要求用户先选工作区。

## 2. 先核对官方来源，再安装

- 读官方资料：项目仓库 README、官方文档或官方站点。用 `yan_web_fetch_text` 抓取已知 URL，用 AnySearch 搜索来源。不要凭记忆编造包名、参数、环境变量。
- 再做机器核对：调用 `yan_mcp_verify_mcp_server`。它会查官方 npm / PyPI registry 中的包，并真实完成一次 MCP 握手列出工具。
- 用户说法与官方不一致（包名拼错、参数写错、地址不是 MCP 端点）时，以官方为准，并在最终回答里说明改了什么、依据是什么。
- 官方资料拿不到时，如实说「未能核对」，不要假装核对过。
- 顺手准备一句「这是什么」：依据官方 README 摘要、registry 描述与握手列出的工具，用中文写一句 ≤60 字的简要说明，安装时一起写入，MCP 服务卡片就靠它显示。

## 3. 按规则安装

- 用核对后的值调用 `yan_mcp_install_mcp_server`。
- 必须带上 `description`（一句中文简介，说明它提供什么能力，≤60 字）。这是卡片上唯一的介绍文字；省略时后端只能用官方 registry 摘要或工具列表兜底，通常不如你写的贴切。
- 核对明确失败（registry 查无此包、握手失败、远程探测失败）时不要强行安装：把失败证据和正确写法告诉用户。只有用户明确接受未核实安装时，才传 `allow_unverified=true`。
- 内置 MCP 不能被覆盖或删除；重复安装同一服务不会新增条目。
- 已有服务若卡片显示「暂无说明」，可以用同名的 `yan_mcp_install_mcp_server` 再调一次补上简介（只补空，不覆盖已有说明）。
- 需要密钥或环境变量才能启动的 MCP，后端不写入明文凭据：如实说明，并让用户在「MCP 服务」页面手动添加。
- 需要移除时用 `yan_mcp_remove_mcp_server`，不要直接改配置文件。

## 4. 交付说明

- 报告：装了什么（名称 / 传输 / 命令或地址 / 简介）、核对证据（registry 包与版本、握手列出的工具数量）、生效时机。
- 生效时机：新 MCP 在下一轮任务生效（当前任务的内核已经启动）。
- 不要只回「已完成」；核对失败、跳过核对或未核实都要写清楚。
